======================================================================
1. PURPOSE OF THIS DOCUMENT
======================================================================

This document explains how WindowsGSM Windrose WorldGuard v2.4.0 behaves with
older/legacy Windrose servers migrated into WindowsGSM.

The main goal of the plugin is to allow an existing server to be managed by
WindowsGSM without losing:

- the existing world;
- player progress;
- server identity;
- WorldIslandId;
- the world's islandId;
- PersistentServerId;
- InviteCode;
- save files;
- the original world structure.

The plugin also allows WindowsGSM settings such as the friendly world/map name,
ports and IP address to be changed without replacing the physical world or
creating a new save.

======================================================================
2. YES, LEGACY SERVERS ARE SUPPORTED
======================================================================

Version 2.4.0 is designed to work with the two main Windrose save/database
formats:

1. Current format:
   R5\Saved\SaveProfiles\Default\RocksDB_v2\

2. Legacy format:
   R5\Saved\SaveProfiles\Default\RocksDB\

The plugin searches for the active world in both locations.

IMPORTANT:
Backup folders such as:

RocksDB_v2_Backups

are not automatically treated as active worlds.

This prevents an old backup from being mistaken for the world that should
actually start.

======================================================================
3. FILES THAT MUST BE PRESERVED DURING MIGRATION
======================================================================

For a safe legacy migration, copy the following items from the old server:

1. Server identity/configuration file:

R5\ServerDescription.json

2. The complete save folder:

R5\Saved\

It is recommended to copy the entire Saved folder rather than only a specific
Worlds directory.

Example source:

D:\OLD_WINDROSE_SERVER\
└── R5\
    ├── ServerDescription.json
    └── Saved\

WindowsGSM destination:

D:\SERVERS\WINDOWSGSM\
└── servers\
    └── <SERVER_ID>\
        └── serverfiles\
            └── R5\
                ├── ServerDescription.json
                └── Saved\

Replace <SERVER_ID> with the actual ID generated by WindowsGSM.

======================================================================
4. SERVER AND WORLD IDENTITY
======================================================================

The following values are critical:

PersistentServerId
WorldIslandId
InviteCode
islandId

They should not be changed unintentionally.

--------------------------------------------------
4.1 PersistentServerId
--------------------------------------------------

Stored in:

R5\ServerDescription.json

It identifies the persistent server.

When migrating an existing server, preserve the original value.

--------------------------------------------------
4.2 InviteCode
--------------------------------------------------

Also stored in:

R5\ServerDescription.json

Keeping the original file normally preserves the existing invitation/server
connection identity.

--------------------------------------------------
4.3 WorldIslandId
--------------------------------------------------

Stored in:

R5\ServerDescription.json

Example:

"WorldIslandId": "E17BEDA81D474B4442824383E2CA9557"

This value tells Windrose which world to load.

--------------------------------------------------
4.4 islandId
--------------------------------------------------

Stored in:

WorldDescription.json

Current Windrose versions use:

"islandId"

with a lowercase "i".

Example:

"islandId": "E17BEDA81D474B4442824383E2CA9557"

This value must match the world directory ID.

======================================================================
5. TYPICAL LEGACY SERVER STRUCTURE
======================================================================

Legacy format:

R5\
├── ServerDescription.json
└── Saved\
    └── SaveProfiles\
        └── Default\
            └── RocksDB\
                └── <GAME_VERSION>\
                    └── Worlds\
                        └── <WORLD_ID>\
                            └── WorldDescription.json

Example:

R5\Saved\SaveProfiles\Default\
RocksDB\
0.10.0\
Worlds\
E17BEDA81D474B4442824383E2CA9557\
WorldDescription.json

The directory name:

E17BEDA81D474B4442824383E2CA9557

should match:

ServerDescription.json:
WorldIslandId

and:

WorldDescription.json:
islandId

======================================================================
6. TYPICAL CURRENT-FORMAT STRUCTURE
======================================================================

Current format:

R5\
├── ServerDescription.json
└── Saved\
    └── SaveProfiles\
        └── Default\
            └── RocksDB_v2\
                └── <GAME_VERSION>\
                    └── Worlds\
                        └── <WORLD_ID>\
                            └── WorldDescription.json

The same identity rules apply.

======================================================================
7. HOW WORLDGUARD VALIDATES A MIGRATED SERVER
======================================================================

Before Windrose is started, the plugin:

1. reads R5\ServerDescription.json;
2. reads PersistentServerId;
3. reads InviteCode;
4. reads WorldIslandId;
5. searches RocksDB_v2 for the world;
6. if needed, searches legacy RocksDB;
7. opens WorldDescription.json;
8. reads islandId;
9. compares islandId with the world folder name;
10. compares the discovered world with WorldIslandId;
11. creates or validates WindowsGSM_Windrose_State.json;
12. only then allows the server to start.

If the identity is inconsistent, startup is blocked before Windrose can
silently create a replacement world.

======================================================================
8. WORLDGUARD STATE FILE
======================================================================

The plugin creates:

WindowsGSM_Windrose_State.json

Normally located at:

<WindowsGSM>\servers\<SERVER_ID>\serverfiles\
WindowsGSM_Windrose_State.json

It stores the protected server/world identity.

Example:

{
  "Version": 1,
  "Locked": true,
  "PersistentServerId": "...",
  "InviteCode": "...",
  "WorldIslandId": "...",
  "FirstLockedUtc": "...",
  "LastValidatedUtc": "..."
}

This file helps prevent accidental identity changes.

======================================================================
9. CHANGING THE MAP NAME IN WINDOWSGSM
======================================================================

In version 2.4.0, WindowsGSM's:

Server Start Map

field is used as the FRIENDLY WORLD NAME.

Example:

Server Start Map:
DELTA

The plugin updates:

WorldDescription.json

field:

"WorldName": "DELTA"

IMPORTANT:

This does NOT change:

WorldIslandId
islandId
PersistentServerId
InviteCode
the Worlds\<WORLD_ID>\ directory name
the physical save files

Example:

Before:
WorldId = E17BEDA81D474B4442824383E2CA9557
WorldName = OLD NAME

You change WindowsGSM to:

Server Start Map = DELTA

Result:

WorldId = E17BEDA81D474B4442824383E2CA9557
WorldName = DELTA

The save remains in exactly the same location.

======================================================================
10. R5WORLDDESCRIPTIONUPDATER.EXE
======================================================================

On current RocksDB_v2 servers, edits to WorldDescription.json must be applied
to the database.

Therefore, when WorldName is changed, the plugin uses:

R5WorldDescriptionUpdater.exe

The plugin searches known locations such as:

<serverfiles>\R5WorldDescriptionUpdater.exe

or:

<serverfiles>\R5\R5WorldDescriptionUpdater.exe

or:

<serverfiles>\R5\Binaries\Win64\R5WorldDescriptionUpdater.exe

If the updater fails:

- startup is blocked;
- the plugin attempts to restore the previous WorldDescription.json;
- the failure is written to the plugin log.

For legacy RocksDB worlds, the plugin does not force the same updater workflow
when it is not required.

======================================================================
11. CHANGING THE IP ADDRESS
======================================================================

Changing:

Server IP Address

in WindowsGSM does not change the world.

It may only affect:

- network interface selection;
- bind address;
- direct connection;
- firewall rules;
- routing;
- port forwarding.

It must not change:

WorldIslandId
islandId
PersistentServerId
InviteCode
save data

======================================================================
12. CHANGING THE PORT
======================================================================

Changing:

Server Port

does not switch or recreate the world.

When:

-wr-direct true

is enabled, the plugin uses the configured Server Port as:

DirectConnectionServerPort

The selected port should be allowed for:

TCP
UDP

When:

-wr-direct false

Windrose normally uses its NAT punch-through/relay behavior, and the
WindowsGSM Server Port is not part of the world identity.

======================================================================
13. QUERY PORT
======================================================================

Windrose does not use a traditional A2S query system like many Steam servers.

Therefore:

Server Query Port

does not select the world and does not alter save data.

It mainly remains because of the generic WindowsGSM server configuration UI.

======================================================================
14. INTENTIONALLY SWITCHING TO ANOTHER WORLD
======================================================================

Changing only:

Server Start Map

does NOT switch worlds.

To intentionally select another existing world, use:

-wr-adopt-world <WORLD_ID>

Example:

-wr-adopt-world E17BEDA81D474B4442824383E2CA9557

The plugin verifies that the requested world exists before changing the lock.

After the switch succeeds, remove the parameter from Additional Parameters.

======================================================================
15. WHAT NOT TO DO
======================================================================

Do not perform the following without a backup:

- rename the Worlds\<WORLD_ID> directory;
- manually change WorldIslandId;
- manually change islandId;
- delete ServerDescription.json;
- copy only part of RocksDB while the server is running;
- run two server instances against the same save database;
- delete WindowsGSM_Windrose_State.json merely to bypass an error;
- copy live save data while Windrose is running.

======================================================================
16. RECOMMENDED LEGACY MIGRATION PROCEDURE
======================================================================

1. Stop the old Windrose server.

2. Stop the Windrose WindowsGSM instance.

3. Verify that these processes are not running:

WindroseServer.exe
WindroseServer-Win64-Shipping.exe

4. Create a full backup of the old server.

5. Install Windrose through WindowsGSM.

6. Do NOT start the new server before migration.

7. Copy:

R5\Saved\

from the old server to:

<WindowsGSM>\servers\<SERVER_ID>\serverfiles\R5\Saved\

8. Copy:

R5\ServerDescription.json

from the old server to:

<WindowsGSM>\servers\<SERVER_ID>\serverfiles\R5\ServerDescription.json

9. If this WindowsGSM instance previously belonged to a different
server/world, remove only the old plugin state file:

WindowsGSM_Windrose_State.json

WARNING:
Only do this when deliberately importing another server identity.

10. Start the server through WindowsGSM.

11. WorldGuard should discover and adopt the migrated server identity.

12. Stop and start the server again to verify persistence.

======================================================================
17. POST-MIGRATION VALIDATION TEST
======================================================================

After the first migrated start:

1. join the server;
2. confirm that the expected world and progress are present;
3. stop the server;
4. start it again;
5. verify the same world loads;
6. change only Server Start Map;
7. start again;
8. verify:
   - the friendly name changed;
   - progress remained unchanged;
   - WorldIslandId remained unchanged;
   - islandId remained unchanged;
   - the world directory remained unchanged.

Then:

9. test a port change;
10. test an IP change if needed;
11. restart again.

None of those administrative changes should create another world.

======================================================================
18. PLUGIN LOG
======================================================================

The log is stored at:

<WindowsGSM>\servers\<SERVER_ID>\serverfiles\
WindowsGSM_Windrose.log

Use this file to diagnose:

- missing world;
- invalid islandId;
- empty WorldIslandId;
- identity conflicts;
- missing updater;
- WorldName synchronization failures;
- recovery failures;
- WorldGuard startup blocks.

======================================================================
19. PLUGIN BACKUPS
======================================================================

The plugin creates small configuration backups under:

<WindowsGSM>\servers\<SERVER_ID>\serverfiles\
WindowsGSM_Windrose_Backups\

They may contain:

ServerDescription.json
WindowsGSM_Windrose_State.json
WorldDescription.json

These backups are not a replacement for a complete backup of:

R5\Saved\

======================================================================
20. SUMMARY
======================================================================

YES, version 2.4.0 is designed to support legacy Windrose servers migrated into
WindowsGSM.

The main requirement is to preserve:

R5\ServerDescription.json
R5\Saved\

The plugin supports active worlds stored in:

RocksDB_v2
RocksDB

Changing the WindowsGSM world/map name modifies only:

WorldName

Changing IP/port settings does not change the world's identity.

The real world identity continues to depend on:

PersistentServerId
WorldIslandId
islandId
Worlds\<WORLD_ID>\

Always keep a full backup before migration or manual save-file changes.
